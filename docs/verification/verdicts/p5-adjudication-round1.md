NEEDS_WORK for three reasons, all repairable and folded into plan v2: (1) a product-goal change it predates — intent and decision records will originate in MULTIPLE spec-development systems, not only Proofbound-native files; (2) the Proofbound identity migration is anticipated in schema names but not operationalized; (3) the enumerated findings below.

## Findings

**F1 (HIGH — product goal: intent is multi-source).** The founder has ruled that business decisions, requirements, and change intents may be authored in external spec-development systems — file-native spec tools (spec-directory conventions of the GitHub spec-kit / AWS Kiro shape) and API-backed in-house design/decision systems — as well as in Proofbound-native committed records. The draft's `internal/connector/records` is therefore one PROVIDER of a missing abstraction, not the architecture. Required: (a) the canonical semantic model (BD/BR/CI, stable obligation identities, typed exact-revision relations) becomes the LEDGER's payload contract, provider-independent; (b) a pinned Intent Provider contract normalizes every source into it; (c) the repo-native records connector is the reference provider; (d) exactly ONE file-native foreign mapper ships in P5 as the contract's discriminating control; (e) API-backed (mutable-upstream) providers are contract-pinned but deferred to a real feed, per the no-primitive-without-a-feed law. A provider that cannot supply a chain segment yields an honest partial chain (`authorization: undeclared`), never a synthesized record.

**F2 (HIGH — identity migration not operationalized).** The product is Proofbound; the plan still specifies `vera` CLI verbs and leaves the rename unplanned. Required: a Task 0.5 with the frozen/live split — the wire names `vera.witness.v1`, `vera.verdict.v1`, `vera.replay.v1` and their pinned byte-exact vectors are FROZEN forever (new schemas take `proofbound.*` names, as this plan's already do); committed verdicts, journals, decision records, and git history stay verbatim; everything live renames now, while zero external consumers exist — the CLI binary (`proofbound`, with `vera` kept one phase as a deprecated alias), the Go module path, docs, and the runtime state directory. Mechanical DoD: a classified case-insensitive inventory of every remaining `vera` occurrence (frozen-wire / frozen-history / alias) with zero unclassified hits; pinned vectors byte-exact; gate green.

**F3 (MED — two digests, one rule).** Relations bind `artifact_sha256` (source revision bytes) while ledger idempotency binds the canonical-payload content digest. Both are correct, but the SPEC must state the two-digest rule explicitly and per provider class: artifact digest = the provider's immutable revision identity (git blob bytes for committed files; canonicalized export bytes otherwise); payload digest = RFC 8785 canonical JSON of the normalized event payload (existing machinery). Fixtures must exercise both digests independently.

**F4 (MED — replay self-sufficiency across providers).** "A fresh clone recovers every referenced revision" only holds when the source IS the repo. General rule: the LEDGER must be replay-sufficient — every id, lifecycle state, typed relation, and obligation statement a verdict can evaluate embeds in the normalized event payload; prose bodies bind by digest and remain the source's artifact. With that invariant, fresh-clone recovery of MEANING holds for every provider by construction, and the draft's option 1 (append-only revision files) is confirmed for the native provider on its own merits.

**F5 (MED — source naming).** A single `records` source overloads the source dimension the moment a second provider exists (the corpus has already paid for this lesson once, on multi-repo tenancy). Recommend sources named `intent.<provider>`; record-id namespaces provider-scoped; cross-provider `supersedes` a typed, tested relation.

**F6 (MED — trailer resolution across providers).** The `Intent:` trailer grammar gains an optional provider qualifier. Unqualified references resolve ONLY against the commit's own tree (the founder-ruled tree-resolution semantics carry over unchanged). Qualified references resolve per the named provider's point-in-time rule, and the RESOLVED digest is recorded in the event — the resolution is the observation. Unknown provider prefix, ambiguous resolution, or digest mismatch fails closed.

**F7 (MED — gate 3's real boundary).** The only delivery boundary Proofbound controls is its own `make delivery-enforce`; that is where `intent-delivery-readiness` graduates, via self-hosting. For any external consumer it remains canary until that consumer's pipeline actually calls the gate. The draft knows observation is not prevention; bind that knowledge to the graduation rule explicitly.

**F8 (LOW — verifier naming).** Replace "Fable" with "independent non-author verifier" in text intended for ratification; a model name is a mechanism detail that belongs in a verdict's provenance header, not in constitution-adjacent prose. Same posture as the corpus's harness-portability rule: named tools are worked examples, never requirements.

**F9 (LOW — provider falsifier).** Add per-provider measurements (records mapped, records rejected by conformance, false-block rate per provider) and one falsifier: if completing a foreign mapping requires changing the canonical schema mid-phase, the canonical model is wrong — STOP and re-ratify; never bend the model to a format.

**F10 (LOW — baseline hygiene).** The handoff's own README-staleness caution is correct; fold it into Task 0's DoD: the ratifying decision's change also fixes the stale README list or records why not, so handed-over context stops contradicting the phase authority.

## Answers to the ten adjudication questions

1. **BD→BR→CI minimal or drift-prone?** Minimal and correct as the canonical LEDGER model — the authorship/cadence table is the argument, and digest-bound relations already contain drift. But as an authoring mandate it over-reaches under multi-source reality: providers supply what they genuinely author, partial chains render as gaps (`authorization: undeclared`), and nothing forces a source to materialize all three types. Keep the three types canonical; drop any implication that every source produces all of them. That is also the strongest anti-bypass design: teams onboard at the segment they actually author.
2. **Immutable files or historical traversal?** Immutable append-only revision files for the native provider — it matches the corpus's supersession-over-edit practice and makes recovery trivial. One-home-per-datum holds because the file owns content and the ledger owns the observation plus digest. Historical blob traversal is rejected: it is more machinery AND it would not generalize to foreign providers anyway. The general answer is F4's replay-sufficiency invariant, which makes fresh-clone recovery provider-independent.
3. **Is CI necessary?** Yes in P5. It carries sponsorship, multi-commit scope, and revision-targeted obligations — and under F1 it gains a fourth job: the cross-source join point, where a commit's claim meets obligations that may live in a foreign provider's requirement. Direct commit→BR binding is a relaxation to consider only if the process-tax falsifier fires. One closed path now.
4. **Authority language?** Yes — declared vs verified is the right boundary. One extension: fields arriving from an external provider are equally DECLARED even when the upstream has its own authentication; upstream attestation metadata is recorded as payload data and never upgraded to verified approval without a Proofbound-authenticated feed. Two states, not three.
5. **Verdict v2 honest?** Yes, with three invariants stated in the SPEC: the verdict owns outcomes and names evidence event ids; builder-authored evidence can never set `SATISFIED`; and cited evidence must exist at ledger sequence at or before the verdict's observation, bound by event id — no future or floating evidence. No additional relationship type is needed in P5.
6. **Tri-state sufficient?** Yes. `UNVERIFIED` as derived-never-stored is exactly right — storing it would create a fourth authored state that decays. Resist adding states; the report-layer chain states already carry the composite story.
7. **Backward compatibility?** Yes, with F2's frozen/live split explicit: `vera.*` v1 wire names and their pinned vectors frozen forever; legacy commits render `intent=undeclared`; no retroactive intent. Historical meaning is preserved precisely because nothing old is renamed or reinterpreted.
8. **Delivery boundary?** Proofbound's own `make delivery-enforce` — the gate graduates there via self-hosting and nowhere else in P5. External consumption stays canary until a real pipeline calls it. Deployment observation is never prevention.
9. **Missing classes?** The provider-conformance family: cross-provider id collision; provider-prefix spoofing in trailers; canonicalization instability (one record, two digests); upstream-mutation digest mismatch; cross-provider sync-ordering (records-before-commits across providers); cross-provider `supersedes`; a foreign fixture whose faithful mapping is IMPOSSIBLE without a canonical-schema change (must STOP, not bend); and the replay-sufficiency probe (drop projections, fresh clone, reconstruct every relation and obligation statement from the ledger alone).
10. **Smallest defensible step?** With exactly TWO providers (native reference + one file-native foreign mapper as the discriminating control) and API-backed providers contract-pinned but deferred: yes. With one provider the abstraction is unproven; with three, or a live API provider, it is premature. Behavior locks, compilers, and ambiguity machinery stay out, as drafted.
