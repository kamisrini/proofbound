## Findings
- **F1 (MED).** frameworks.go:74,82,83,99,107,180 and the generated document. Reasons claim outcomes the controls do not produce: C9 CC6.1 and the Agents paragraph "a commit signed by a declared key proves which person or agent made it" (it proves only that a declared key's holder signed; an agent run with a human's key or a shared key defeats it); C6 PS.1 "protect the code and its controls" (C6 only lists); C6 PO.3 "is itself under change control" (listing is not change control); C5 "the population of changes is complete" (only relative to git rev-list of the range); C10 A.8.4 "declared and checked" (detective, after the fact; A.8.4 is about managing access). An auditor or buyer quotes the reason as a factual claim; the page caveat does not undo it. Fix: write each reason as "evidence toward <criterion subject>: <what the control does>"; consider a test refusing "proves", "ensures", "protects", "complete".
- **F2 (MED).** frameworks.go:51,52,63,69,95; spec :25. Stretched mappings: SOC 2 CC3.4 is entity-level risk assessment (COSO Principle 9), not requirement drift; CC8.1 already covers C4, so drop it. ISO A.8.29 is security testing; C1's review of functional promises is not, so drop it. SSDF PS.2 (PS.2.1, integrity verification information for released software) is at most partial ("integrity of the reviewed source revision, not of built artifacts"); "exactly what a warranty bundle is" overstates. SSDF PW.7 does not require reviewer independence; the C1 and C8 reasons attribute it. Fix: drop CC3.4 and A.8.29, qualify PS.2 as partial, reword PW.7 to "records a code review per change; whether it covers security requirements is the reviewer's scope".
- **F3 (MED).** frameworks.go:58,89; spec :38. Art. 17(1)(b) is design, design control and design verification; development, quality control and quality assurance is (c), so C2's "design and development control" cites (b) for (c), and (c) is never mapped despite the spec saying (b)-(d). Omitted: Art. 17(1)(a) (compliance strategy including procedures for the management of modifications, the Act's change-management hook: C1, C2, C5, C10); Art. 17(1)(k) (record-keeping of all relevant documentation: C3, C5); Annex IV point 2(g) (validation and testing procedures, test logs and reports signed by responsible persons: C1, C8). Fix accordingly; the test regex already allows (a)-(m).
- **F4 (LOW).** Better or omitted criteria: SOC 2 CC6.2/CC6.3 fit C6's changes to who may sign better than CC6.1; C8's CC5.1 rests on its segregation-of-duties point of focus and should say so; ISO A.8.30 (outsourced development, the closest analogue for agent-written code) and A.8.15/A.5.33 (logging, protection of records); SSDF PO.3.3 (tools generate artifacts as evidence of practices), PO.4.
- **F5 (LOW).** frameworks_test.go:22. The format regexes accept CC9.9, A.6.37 and RV.9; the golden catches changes, not wrong IDs, and the document prints no criterion titles. Fix: an allowlist criterion → official title per framework, tested, and printed in the document.
- **F6 (LOW).** frameworkDocURL (frameworks.go:123) points to main, so a v0.3.2 binary can link to a mapping that differs from the one it shows (pin to the tag or serve locally); the per-card "Maps to" line has no caveat, so a screenshot of one card loses it; use "ISO/IEC 27001"; give the EU AI Act an "as of" date (high-risk dates subject to the pending Digital Omnibus amendment); check whether SP 800-218 Rev. 1 (v1.2) is final.
- **F7 (LOW).** frameworks_test.go:16. The package-global flag name `update` panics at init if another test file defines it, and `go test ./... -update` fails in other packages; rename to -update-framework-map.
