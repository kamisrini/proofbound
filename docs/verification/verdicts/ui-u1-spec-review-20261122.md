## Status
NEEDS_WORK: 2 HIGH, 9 MED, 1 LOW group. The Host check is sound against DNS rebinding; the token scheme is not sufficient against other local clients, and the signed-record trust model lets an excepted commit's author close its own exception.

## Findings
- **F1 (HIGH).** ui-u1-audit-room-spec.md section 4 "Write safety" — the per-run token is embedded in the page served to any GET that has a loopback Host. Any other local process or user (shared host, WSL/Windows side, a compromised dev dependency) fetches `/audit`, reads the token, sets `Origin` itself (not a browser) and POSTs `/act/sign`, which signs with the victim's key. Host/Origin/token only stop browsers. Fix: do not embed the token in a page served unauthenticated. Print a capability URL with the token in the fragment or a one-time `?t=` exchanged for an `HttpOnly; SameSite=Strict` cookie, put the same secret check on every request, compare in constant time, and keep it out of `xdg-open` argv where `ps` shows it (or send `--open` through the exchange). State that the threat model excludes or includes other local users, and test both.
- **F2 (HIGH).** section 4 "Identity" and "Reading records back" — a verified outcome needs only a key declared at HEAD. A commit's author can add `.proofbound/keys/me.pub` and `.proofbound/outcomes/<own-exception>.json` in the same range (C6 lists the key but not the outcome, and the outcome is housekeeping), and the page then shows the exception closed and signed. No rule separates the signer from the author of the excepted commit (Law 9) or from keys added in the range. Fix: require the signer's key to be declared at the audit's base (or before the excepted commit) and the signer not to be the commit's author key/identity; show "key added in this range" prominently; add `.proofbound/outcomes/`, `.proofbound/attestations/` and `.proofbound/sdd-profile.json` (who owns specs) to C6.
- **F3 (MED).** section 4 "Reading records back" — verification lists well-formed, tag, key, signature, but not: `exception` field equals the filename stem and the id's kind/commit12 matches `commit`; `outcome` in the enum; strict parse (no unknown or duplicate keys, file bytes equal canonical plus one newline); size cap. Without the stem binding, a validly signed record for `gate-X` copied to `warranty-X` or `order-X` closes a different exception than the signer saw. The signature also covers no digest of what the exception was (reason text, paths), so "accepted" is not bound to evidence. `fixed_by` only "resolves to a commit": it need not be in the range, an ancestor of HEAD, or touch the same paths, and `reverted` is never checked, yet both show as closed. Fix: add these checks, include an `evidence_sha256` of the exception row in the signed record, require `fixed_by` to be a descendant of `commit` within HEAD, and label fixed/reverted as "signer states" unless checked.
- **F4 (MED).** section 4 "Flow" — `/act/sign` takes "the same fields" and re-validates, but `at` and the final bytes are not stated to be those previewed. The person may sign a record they did not see (different `at`, or a changed exception after re-audit). Fix: preview returns the record plus a digest; sign must send the digest, and the server refuses if the re-computed record differs (including a changed exception list or HEAD). Also reject Unicode format/bidi characters (Cf) in `reason`, not only control characters.
- **F5 (MED).** section 1 — (a) `base` is passed into `git rev-list <base>..HEAD`; a value like `--output=...` parses as an option. Resolve with `rev-parse --verify --end-of-options <ref>^{commit}`, then use only the 40-hex. (b) The default base "root commit" is excluded from `base..HEAD`, so the root commit (and in a one-commit repo, everything) goes unaudited. Include it (`rev-list --root`) or say so. (c) A base that is not an ancestor of HEAD, equals HEAD, or leaves an empty range reads as controls "held" with 0 commits; show an explicit "empty range / base not an ancestor" state.
- **F6 (MED).** sections 2 and 4 — "No GET request writes anything" is false: every `GET /audit` runs `sync all`, which appends ledger events and projections, and any cross-site page that can guess the port can trigger it (Host is correct for a cross-site GET). Test `GET never writes` (section 7) cannot pass or is vacuous. Fix: make refresh an explicit POST (token-guarded) or reword the invariant to "no repository file, and no git state" and enumerate the ledger writes; the audit should render the ledger as it stands, with a Refresh button.
- **F7 (MED).** section 3 C3 — overclaims and misfires. (a) "Carries a warranty" is checked by synthesizing one on the auditor's machine with the auditor's key and `time.Now`; no issued warranty artifact is examined, so a pass means "could be issued here", not "the author carries one". (b) `buildWarranty` loads `gates/` from the working tree, not HEAD (warranty.go:221), unlike claims verified at HEAD in the PR check; a dirty tree changes the result. (c) With a local key that is not declared at HEAD, verification fails for every PASS commit, producing a false `warranty-*` exception each; the spec only handles "no local key". (d) The result depends on whose machine runs it, so it is not reproducible (see F9). Fix: read gates from HEAD, treat an undeclared key as NONE with its own basis line, rename the control to what it checks, and state it is machine-dependent.
- **F8 (MED).** section 3 C5, C6, C7 — C5 is a tautology: housekeeping is defined as "no claim and not uncovered", so the sum cannot differ from the rev-list count; it claims an accounting check it cannot fail, and the control counts as HELD. Either derive classes independently (e.g. also cross-check against `git rev-list --count`) or drop it from the held tally. C6 needs `--name-status` to separate modify/delete from add, and with `--cc` merges that prints per-parent letters; specify it, and the gates/ adds exemption means a weak new gate is only caught by C1. C7: commits with two valid claims, or any claim that is not exactly one, are silently skipped (no exception and no NONE note); the archive pattern `archive/*-<name>/` disagrees with `changeExists`, which uses `archive/<name>`; the claim name is not validated against `taskNameRE`, so `sdd:../x` reaches a tree path lookup.
- **F9 (MED).** section 4 attestation — `transcript_sha256` is the hash of a report that includes C3 (machine/key dependent), C4 (local ledger and sync state, and `reportDrift` is ledger-wide, not range-scoped), outcomes read from HEAD (which moves with every recorded outcome and with the attestation commit itself), and the head used for gates/keys. "Equals the transcript of that same range now" will usually be false, or true only on the signer's machine, so the attestation cannot be verified from a clone. Fix: define the transcript as a pure function of (base, head) read from those commits' trees, excluding C3/C4 or recording them as non-reproducible fields outside the hash; fix the attestation to the HEAD at sign time and refuse if HEAD moved.
- **F10 (MED).** section 4 "Flow" — commit safety. (a) On commit failure the file stays and "never overwritten" blocks any retry, so the exception is stuck (and an invalid record committed by anyone squats the id). Fix: allow re-sign when no verified record exists at HEAD, replacing an uncommitted or non-verifying file. (b) HEAD can move between audit and sign (other terminal): re-check HEAD equals the audited head. (c) `git commit -- <path>` is the `--only` form so other staged changes stay staged, which is right, but it fails mid-merge/rebase ("cannot do a partial commit during a merge"), on an unborn HEAD, with missing `user.name`, with GPG-signing prompts, and on detached HEAD the commit is orphaned by the next checkout. Specify the preconditions and the messages for each, and say a record is only counted once it is reachable from HEAD. (d) Tenant pre-commit hooks and the repo's own delivery rules (decision commits need an Intent trailer) may reject the commit; the prepare-commit-msg stamp does not fire for housekeeping paths (task.go:169), so that part is fine.
- **F11 (MED).** section 2 — "never waits indefinitely" contradicts "serialized by one mutex": a second tab blocks behind a long `sync all`. Use `TryLock` (or a bounded wait) and answer 503. Specify a request timeout and that client disconnect cancels the sync, and that Ctrl-C mid-request releases the lock (store lock is flock-based and returns `ErrLocked` immediately, which is good). The 503 also needs to distinguish "busy" from other store errors.
- **F12 (LOW, grouped).** (a) Section 7 tests do not prove the rows. TestUIJSONTwin compares JSON to a report from the same handler, so it cannot detect HTML divergence; assert specific rendered values. No test for C3, C4, C6 add/modify/delete, C7 root and merge commits, empty range, 503 busy, sign-flow (only-path commit with other staged changes, failure leaves file, existing record refused), HTML escaping of a `<script>` commit subject and path (CLI-INV-38 has no test row for it), CSP/nosniff/referrer headers, or the guards on `/static` and `/transcript`. TestUIRequestGuards needs hostile Host values (`localhost.evil.com:port`, uppercase, trailing dot, wrong port, `@`), missing Origin, `Origin: null`, and an assertion that the file and git state are unchanged after each rejection. TestOutcomeRecords needs the filename/exception mismatch, strict-parse and duplicate-record cases from F3. (b) Embedded JS that renders preview or error text must use `textContent`, not `innerHTML`; add `base-uri 'none'; form-action 'self'` to the CSP. (c) C4 parses human drift text; prefer a structured call, and say it covers all warranties, not the range. (d) The same public key declared under two names makes `by` ambiguous. (e) Per-request C3 over many PASS commits is O(n) git/ledger work; cache per HEAD. (f) Signature domain separation is adequate: the two new tag lines are distinct from `proofbound.review-signature.v1`, `proofbound.warranty-cosignature.v1` and the warranty schema tag, and sign over tag plus canonical bytes. Add a test that each existing verifier rejects the new records and vice versa.
