# VD-commit-is-durability-6p29qf: committing is durability, not acceptance — never withhold a commit pending a verdict

**Status:** Accepted
**Date:** 2026-08-09
**Context:** During P1 Task 3 roughly 8,700 lines of a finished package (`kernel/internal/store`) sat uncommitted across six adversarial review rounds, because the executing agent had bound "commit" to "an independent verifier returns ACCEPTABLE". This repo is local-only with no remote by design ([[VD-local-only-backup-mjic4a]]), so the working tree was the single copy of the work and the newest backup bundle predated the entire package. A machine failure at any point that day would have destroyed it. The existing control, `make wrap-verify`, requires a clean tree — but only at `/vera-wrap`, so a long session that never wraps never trips it. That is exactly what happened: the risk was invisible for an entire session and was caught by the founder, not by the build system.
**Decision:** Committing and accepting are separate concerns and are never coupled. **Committing gates DURABILITY; verification gates ACCEPTANCE.** A commit to this repo publishes nothing (there is no remote) and is undone by amend, reset, or revert, so withholding one buys no safety and risks total loss. Work is checkpoint-committed as it becomes coherent, and a pending verdict is recorded IN THE COMMIT MESSAGE rather than expressed by refusing to commit. The rule "only a non-author verdict may accept" stands unchanged — it governs whether work is trusted and built upon, never whether it is written to disk. Enforced mechanically by `scripts/commit-cadence.sh`, which runs inside `make check` and BLOCKS once uncommitted work is older than 90 minutes (`COMMIT_CADENCE_MINUTES` widens the window for one genuinely indivisible artifact, and the reason is journaled).
**Consequences:** Uncommitted work can no longer accumulate invisibly, because the check runs continuously during a session rather than only at wrap. Accepted cost: history carries checkpoint commits whose content had not yet been verified, so a commit is no longer evidence that anything was reviewed — commit messages must state verification status explicitly, and `notes/state.md` must distinguish COMMITTED from VERIFIED. A rejected checkpoint costs one `git revert`. Also fixed while implementing: both `commit-cadence.sh` and the pre-existing `wrap-verify.sh` used `git status --porcelain`, which collapses an untracked directory to a single `?? notes/` entry, so the `notes/tmp/` scratch exemption never matched; both now pass `-uall`. Caught by the new script's own self-test.
**Revisit when:** a remote is added (publication changes what a commit means, and this record's reasoning must be re-derived); or the 90-minute window proves wrong in practice — too tight and it interrupts genuine single-artifact stretches, too loose and it stops catching the failure it exists to catch.
