# 2026-09-13 — P6 dual-platform decision

The founder responded “okay, i like the idea.” to the recommendation to support both Linux and
native Windows, using Git Bash/MSYS2 behind the PowerShell setup and check entry points. I recorded
that statement verbatim in `docs/verification/verdicts/p6-dual-platform-ratification.md` and minted
`docs/decisions/VD-p6-dual-platform-2026-09-13.md`.

The Task 3 reproducibility SPEC now defines the dual-platform prerequisite and acceptance contract:
native Windows must not be substituted by WSL, and C8-002 requires a real green native run with
tool versions, `make check`, witnessed ledger checks, two-pass sync, verify, rebuild equality, and
self-hosted reports. The prior Windows `make`-missing run remains red historical evidence until
that acceptance is completed. The fresh-clone historical-evidence portability blocker C8-001 is
unchanged and remains a separate founder decision.

The derived decisions index was regenerated. No Windows implementation or green acceptance is
claimed by this entry.

The native Windows inventory found Git, Go, and `jq`, but no GNU Make, `golangci-lint`, or `rg`; the
available `bash` command was the WSL launcher, while Git Bash existed at the expected Program Files
path. The first `setup-windows.ps1 -InstallTools` attempt began an unnecessary Go MSI upgrade and
stalled without progress, so it was stopped. The setup script was corrected to install only missing
packages and now explicitly checks Git Bash and ripgrep. `scripts/tests/windows-contract.test.sh`
passes; no Windows gate result is claimed yet.

The native acceptance work then used the official Go 1.27.0 Windows archive, a Windows-filesystem
checkout with `core.autocrlf=false`, and the installed native Make, golangci-lint, and ripgrep. The
WSL UNC attempt was stopped after Go reported `RLock ... Incorrect function`; this was not accepted as
Windows evidence. The Windows gate exposed three repository-tool portability defects: default GNU
Make did not select `Makefile` on the case-sensitive mount, invariant-lock generation depended on
locale ordering, and identity inventory parsed Windows drive/path output incorrectly. These were
fixed in commits `dc7d587`, `423e74a`, `f46606d`, and `a26f3e5`; the focused tests and host Linux
`PATH=/home/thamm/go/bin:$PATH make check` passed. The latest native run passed compilation and all
checks through identity/census validation, then correctly stopped at `state-freshness` because the
resume note was four commits behind HEAD. C8-002 remains unclosed pending a rerun after this state
refresh.

LESSON[registered-tag:resume-state-freshness]: A chain of small, coherent portability fixes can
exceed the three-commit state freshness limit before the next wrap. Refresh the top resume note and
journal before the next acceptance rerun so the guard remains a useful stop rather than a late surprise.

The native run at the connector-evidence commit reached the PostgreSQL-backed kernel suite after
passing the fast checks, then exposed the Unix-only store `syscall.Flock` call. I amended the store
SPEC before adding POSIX/Windows lock adapters, cross-compiled the store for Windows, and passed its
Linux regression suite. The full gate also exposed POSIX-only signal tests and Windows-illegal Git
filename fixtures; the relevant SPECs now state those host constraints and the tests retain the
stronger Linux assertions while using legal Windows fixtures. The connector closure generator and
artifact were regenerated when its bound commit changed. The next native run is unverified.

LESSON[registered-tag:resume-state-freshness]: State freshness is a gate, not a wrap substitute;
after a sequence of required source/spec/generated-artifact commits, refresh notes/state.md before
starting another long acceptance run.
