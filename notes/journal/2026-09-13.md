# 2026-09-13 — P6 dual-platform decision

The founder responded “okay, i like the idea.” to the recommendation to support both Linux and
native Windows, using Git Bash/MSYS2 behind the PowerShell setup and check entry points. I recorded
that statement verbatim in `docs/verification/verdicts/p6-dual-platform-ratification.md` and minted
`docs/decisions/VD-p6-dual-platform-2026-09-13.md`.

The Task 3 reproducibility SPEC now defines the dual-platform prerequisite and acceptance contract:
native Windows must not be substituted by WSL, and C8-002 requires a real green native run with
tool versions, `make check`, witnessed ledger checks, two-pass sync, verify, rebuild equality, and
self-hosted reports. The prior Windows `make`-missing run remains red historical evidence until
that acceptance is completed. The fresh-clone historical-evidence portability blocker C8-001 is
unchanged and remains a separate founder decision.

The derived decisions index was regenerated. No Windows implementation or green acceptance is
claimed by this entry.

The native Windows inventory found Git, Go, and `jq`, but no GNU Make, `golangci-lint`, or `rg`; the
available `bash` command was the WSL launcher, while Git Bash existed at the expected Program Files
path. The first `setup-windows.ps1 -InstallTools` attempt began an unnecessary Go MSI upgrade and
stalled without progress, so it was stopped. The setup script was corrected to install only missing
packages and now explicitly checks Git Bash and ripgrep. `scripts/tests/windows-contract.test.sh`
passes; no Windows gate result is claimed yet.

The native acceptance work then used the official Go 1.27.0 Windows archive, a Windows-filesystem
checkout with `core.autocrlf=false`, and the installed native Make, golangci-lint, and ripgrep. The
WSL UNC attempt was stopped after Go reported `RLock ... Incorrect function`; this was not accepted as
Windows evidence. The Windows gate exposed three repository-tool portability defects: default GNU
Make did not select `Makefile` on the case-sensitive mount, invariant-lock generation depended on
locale ordering, and identity inventory parsed Windows drive/path output incorrectly. These were
fixed in commits `dc7d587`, `423e74a`, `f46606d`, and `a26f3e5`; the focused tests and host Linux
`PATH=/home/thamm/go/bin:$PATH make check` passed. The latest native run passed compilation and all
checks through identity/census validation, then correctly stopped at `state-freshness` because the
resume note was four commits behind HEAD. C8-002 remains unclosed pending a rerun after this state
refresh.

LESSON[registered-tag:resume-state-freshness]: A chain of small, coherent portability fixes can
exceed the three-commit state freshness limit before the next wrap. Refresh the top resume note and
journal before the next acceptance rerun so the guard remains a useful stop rather than a late surprise.

The native run at the connector-evidence commit reached the PostgreSQL-backed kernel suite after
passing the fast checks, then exposed the Unix-only store `syscall.Flock` call. I amended the store
SPEC before adding POSIX/Windows lock adapters, cross-compiled the store for Windows, and passed its
Linux regression suite. The full gate also exposed POSIX-only signal tests and Windows-illegal Git
filename fixtures; the relevant SPECs now state those host constraints and the tests retain the
stronger Linux assertions while using legal Windows fixtures. The connector closure generator and
artifact were regenerated when its bound commit changed. The next native run is unverified.

LESSON[registered-tag:resume-state-freshness]: State freshness is a gate, not a wrap substitute;
after a sequence of required source/spec/generated-artifact commits, refresh notes/state.md before
starting another long acceptance run.

The native Windows gate was rerun from a fresh checkout at `59814ad`. Corpus, generated-freshness,
census, registry, backup, and the PostgreSQL-backed test phases ran; the gate failed at `skip-lint`
because the Windows/POSIX-bound skips introduced by the portability work were not declared, and
`p6-connector-reality.md` still named the prior connector commit. I added the explicit allowlist
entries and regenerated the connector artifact. No green C8-002 result is claimed; the next run
must be from a fresh bundle containing these changes.

LESSON[registered-tag:native-skip-declarations]: Platform-specific skips are part of the executable
verification contract. Add their allowlist declarations in the same coherent change as the SPEC/test
boundary so a long native run cannot reach the final gate with an undeclared result.

The first complete native witnessed acceptance reached `sync all` after a green bare Windows gate,
but both sync passes failed closed in the Git connector because a detached checkout has no output
from `git show-ref`; the existing validator incorrectly treated that status as broken even when
`HEAD` had already been validated as a commit. I amended the gitcmd SPEC, removed the erroneous
rejection, added a direct detached-HEAD regression test, and regenerated the connector evidence in
commit `01e0dc9`. C8-002 remains open until a fresh native gate and the full witnessed acceptance
sequence pass.

LESSON[registered-tag:detached-head-acceptance]: Fresh detached checkouts are part of reproducibility
evidence; do not infer ref corruption from `git show-ref` exit 1 without considering a valid detached
`HEAD`.

The final native Windows acceptance was run from a fresh Windows-filesystem checkout at `a2e3aed`.
The PowerShell entry point and bare gate passed, the witnessed gate passed with one published witness,
and two complete sync passes passed with first-pass counts `intent=3 git=197 checks=1 reviews=23
sessions=0` and second-pass counts all zero. Native verify then failed closed on the known dangling
historical event `01M28TPW9C8R7ND19MNDCJ9GDG`, exactly matching the Linux blocker. I recorded the
tool versions and results in `docs/verification/p6-windows-platform.md`; C8-002 remains open because
the Task 3 acceptance requires verify, rebuild equality, and self-hosted reports after the shared
C8-001 historical-evidence decision.

LESSON[registered-tag:shared-verification-blocker]: A platform-specific green gate does not close a
reproducibility row when the same source-ledger evidence fails in every fresh OS ledger; bind the
platform result, preserve the shared failure, and stop at the ratification gate.

A final Linux bare `make check` retry used host execution with a clean Linux PATH. Repository shell,
census, backup, and generated-freshness checks passed, but `scripts/kernel-check.sh` stopped with
`golangci-lint: command not found`; no Linux linter binary is installed in this workspace. This is
recorded as unverified rather than conflated with the green native Windows gate.

LESSON[registered-tag:toolchain-separation]: Cross-platform acceptance requires platform-native
toolchain evidence; a Windows linter executable cannot substitute for a Linux linter in a Linux
bare-gate claim.

The ratified option-1 historical archive was accepted on a clean native Windows filesystem checkout

The first Windows retries were not treated as evidence: overlapping disposable test trees caused

After verified cleanup and a single isolated process tree with the complete native tool PATH, the

LESSON[registered-tag:native-acceptance-isolation]: A long native gate must be run as one isolated
process tree with explicit shell-tool paths; before retrying, inspect and terminate only verified
leftover test processes from the disposable checkout. Record environmental failures separately from
repository failures and never close a census row on a partial run.

Task 4 began after Task 3 closure. I wrote the ratified path-only applicability SPEC and invariant
tests before implementation, then added `scripts/intent-applicability.sh`. The suite covers the exact
include/exclude universe, content-independent matching, root and ordinary commits, deletion,
rename/copy path handling, and invalid-commit fail-closed behavior; it passes. The matcher is not
yet wired into `make delivery-enforce`, and the complete post-`f426ca8` canary report is still open.

LESSON[registered-tag:spec-first-applicability]: A path-only policy needs hostile Git-history
fixtures, not just filename examples; copy detection can make an excluded new path applicable when
its included source is part of the same change, so fixtures must use distinct content and assert
both paths explicitly.
