# Journal — 2026-08-12

## invariant-lint has been blind to every connector package

Task 4 opened with `/vera-spec` for `internal/connector/git`. The SPEC cites fifteen tests, none
of which exist yet — and `invariant-lint` reported **clean**.

Cause: the lint globbed `kernel/internal/*/SPEC.md`, one level deep. `core` and `store` sit there;
`connector/git` is two levels down, so the gate never read it. **Tasks 4 through 7 are all
connectors**, which means the invariant table for over half the remaining P1 packages would have
been unenforced while the gate printed success — for the fourth time this week, a check that could
not fail.

Found by accident, and worth naming how: I wrote a SPEC full of citations to tests that do not
exist and expected the gate to reject it. When it passed I did not believe it. Writing a spec
BEFORE the tests turns the gate into its own probe — Law 6's side effect.

Switched from a one-level glob to `find kernel -name SPEC.md`. It now correctly refuses the new
SPEC with fifteen dangling citations, which is the SPEC's honest status until the tests land.

LESSON[wrong-target]: a gate's SCOPE is as load-bearing as its logic, and a scope bug is silent by
construction — the gate reports on what it read, never on what it missed. This one had been narrow
since 08-09 and passed every run.
Compiled response: `scripts/invariant-lint.sh` walks `find kernel -name SPEC.md` rather than a
fixed-depth glob. The general form is owed and recorded: no other gate has been checked for scope
blindness, and `figure-provenance` uses a hardcoded two-path list that will have the same problem
when a third SPEC-bearing tree appears.

## Task 4 — the git connector, and four things the red state found

Wrote the SPEC first (17 invariants after two appends), then all 17 tests, then the implementation.
Every step in that order paid.

**The red state was informative, deliberately.** The skeleton returned a named `ErrNotImplemented`
from every function instead of not compiling, so all 17 tests failed on their own assertions rather
than as one build error. Reading that failure list was how three of the four findings below
surfaced — a package that merely fails to build tells you nothing about which invariant is unproven.

**1. The SPEC asserted more than the code promises.** INV-12 said a control character in a commit
SUBJECT is refused by core. It is not: core guards control characters in `native_id` and
`connector_version` — the fields that reach logs and CLI output verbatim — and treats payload
content as opaque JSON, where NUL escapes legally. git also refuses NUL in a commit message, so
the input cannot arise. The test written from that line failed against CORRECT code.

The temptation was precise and worth naming: add a control-character check to `core` so the SPEC
becomes true. That would have been scope creep into a package I am not building, in service of a
claim nothing needed. Corrected the SPEC instead, in place, with the reasoning recorded so the line
is not silently reworded back.

LESSON[spec-asserts-more-than-code]: an invariant can be wrong, and the failure mode is a test that
fails against correct code — which reads exactly like a bug. When a test written from the spec
fails, the spec is a suspect, not just the code. Writing tests from the SPEC rather than from the
implementation is what makes this detectable at all.
Compiled response: none available as a script — this needs judgement per case. Recorded as a
review question instead: for every red test, ask "is the ASSERTION right?" before touching code.

**2. `exec` cannot carry a NUL in an argument.** `gitcmd` framed `git log --pretty` output with
literal `\x00` field separators built into the format STRING. An argv string is NUL-terminated by
the kernel, so exec failed with "invalid argument" before git ran. git's own `%x00` escape makes
git emit the byte. Two spellings of the same separator now sit side by side with a comment saying
they must stay in step.

This surfaced ONLY because the rewrite tests drive real git. A fake `Repo` returning canned commits
would have passed forever, and the connector would have failed on first real use.
LESSON[fake-proves-the-fake]: when a property belongs to an external tool (does amend change the
SHA? can argv hold a NUL?), a fake asserts my belief about the tool back at me. The two-package
split — pure `git`, impure `gitcmd`, rewrite tests against real repositories in `t.TempDir()` — was
justified in the SPEC as necessary for INV-6/7/8 and earned itself again here.

**3. A self-test poisoned the gate it guards.** `link-lint` needed a change (tests that parse
decision citations need id-shaped strings that are not citations, so `VD-fixture-<6>` is now
reserved). It had NO self-test — it predates that rule — so I wrote one. The self-test's fixture
ids, written as literals, were then picked up by the real repo-wide scan and reported as broken
references in vera-core itself.

Fixed by assembling the ids at runtime (`P=VD; GHOST="$P-ghost-bbbbbb"`) so no id-shaped literal
exists in the file. The alternative — excluding `scripts/tests/` from the scan — would have blinded
the gate to genuine broken citations in test scripts, trading a real check for a cosmetic one.
LESSON[self-test-poisons-its-gate]: a self-test for a REPO-WIDE scanner lives inside its own search
space. Fixture data that looks like real data will be found as real data.
Compiled response: `scripts/tests/link-lint.test.sh` assembles every id at runtime; the comment
says why, so the next person does not "simplify" it back into literals.

**4. The exemption was bounded on the wrong axis, and the gate said so.** First cut exempted
`VD-fixture-` only inside `*_test.go`. `make check` then failed on the SPEC's own § 5.1 pinned
vector, which quotes the fixture payload verbatim. That is not a citation either — and forcing a
real id there would be wrong twice: the fixture commit never cited that decision, and renaming the
decision would re-key a pinned `content_sha`. Widened to `*_test.go` + `SPEC.md`, with a
still-BLOCKS control case for each so the exemption cannot quietly become an off switch.

**Evidence the morning's fix was real.** With `invariant-lint` now reading connector SPECs, it
immediately caught three tests whose names diverged from SPEC § 5. Direction of repair matters: the
SPEC is the authority written first, so the TESTS were renamed to match it — and the SPEC's names
were the better ones (`AmendAppendsTheNewShaAndKeepsTheOld` states the append-only point that
`AmendAppendsExactlyOneEvent` leaves implicit).

LESSON[gate-without-self-test]: `link-lint` and `index-check` predate the self-test rule and still
lack coverage of their older behaviour. `link-lint` now has 11 cases. `index-check` remains owed —
recorded rather than done, because doing it here would be scope creep on Task 4.

## Round 1 on the git connector: NEEDS_WORK, and what it says about how I write code

Three lenses plus an adjudicator, all calibrated. 4 HIGH, 7 MED, 4 LOW, and the SPEC false in
eleven places — on a package that had passed `make check` GREEN with 17 invariants and a mutation
sweep I ran myself. That gap is the whole finding.

**Every HIGH was a DECISION made silently in `gitcmd`.** Not a coding error: a choice about what the
system does — what counts as a ref, what to do with a shallow clone, how to frame output, whether a
broken repository is distinguishable from an empty one — made in passing, recorded nowhere, tested
not at all. I had justified that package to myself as "a thin translation layer that owns no
invariant of its own", and wrote exactly that in SPEC § 6.

LESSON[thin-layer-is-self-fulfilling]: describing a component as decision-free is what stops anyone
looking for its decisions. The phrase was in the SPEC as a REASON it needed no tests, and four HIGH
defects lived behind it for a day. The trigger § 6 itself named ("if it ever grows a decision of its
own it earns a SPEC") had already fired before the ink dried — I just had no mechanism that would
notice, because the mechanism I would have used was the sentence claiming there was nothing to see.
Compiled response: `gitcmd/SPEC.md` exists with 21 invariants and a test file. The general form is
owed and recorded: no other component described as "thin" has been checked for the same thing —
`internal/projections` and `internal/connector/checks` are both currently `[no test files]`.

**The framing defect is the purest instance of my recurring failure mode.** I reasoned: git refuses
NUL in a commit message, therefore NUL-adjacent framing is safe. True. Then I wrote a record
separator of 0x1e and carried the conclusion across, in a comment asserting "this framing cannot be
broken by commit content". git does not refuse 0x1e. A plain `git commit -m` with a pasted terminal
escape triggers it, and because the parse failure aborts the whole listing, ONE such commit stops
the repository ingesting entirely.

LESSON[claim-in-a-comment-reads-as-verified]: I stated it as settled fact in a code comment, which
is the most authoritative-looking place to put an unverified claim — the next reader (including me)
treats it as something that was checked. I even flagged it to the reviewers as "a claim, not a
fact", which means I KNEW it was unverified and shipped it in the assertive voice anyway. Writing
"cannot" is a commitment to have tested it.
Compiled response: G-INV-1 with four hostile fixtures. No general script — the durable form is the
review question already recorded: for every "cannot/never/always" in a comment, name the test.

**The sharpest finding was about tests, not code.** INV-6/7/8 exist to prove a date watermark cannot
work. A reviewer installed a real watermark and all three still PASSED, because my fixture pinned
GIT_COMMITTER_DATE to one constant for every commit — so no date filter could exclude anything.
These were not vacuous tests: they were real, they asserted real things, they killed real mutations.
They simply could not discriminate the property they were named for.

LESSON[fixture-holds-the-variable-constant]: a test can be correct, non-vacuous, mutation-killing
and STILL unable to detect the thing it exists to detect, when its fixture holds constant the
variable the property is about. This is a category beyond "assertions that cannot fail" — the
assertion can fail, just never for the reason claimed. Ask of each test: what is the property ABOUT,
and does the fixture VARY that thing?
Compiled response: dates now advance per git invocation, and INV-18 states the property directly (a
commit dated before one already ingested is still ingested) rather than hoping three other tests
imply it.

**One vector pins one branch.** The § 5.1 pinned vector promised that changing the normalisation
"fails HERE first". Flipping empty-slice handling from `null` to `[]` — which re-keys every commit
citing no decision, i.e. nearly all of them — survived, because the vector's slices were both
non-empty so the branch was never taken.
LESSON[vector-covers-only-its-own-path]: a golden vector proves the path it walks. Enumerate the
branches the value can take and pin one per branch. Compiled response: a second vector; the general
form is the same coverage question every pinned artifact should answer.

**What the round cost and returned.** ~940k subagent tokens, ~53 minutes wall clock, 15 findings, of
which I independently reproduced the two I spot-checked before acting, and zero were discarded by the
adjudicator for lack of proof. Against that: `make check` was GREEN throughout, so every one of these
would have shipped.

## Round 2: NEEDS_WORK again, and the pattern is now the finding

Round 1: 15 findings. My remediation closed 9, left 6, and introduced new ones. Round 2: 4 HIGH,
9 MED, 8 LOW. The adjudicator's verdict on my repair work: *"Both SPECs are less true than they
were before round 2's remediation on at least one axis each."*

Two rounds, ~1.93M subagent tokens, ~2 hours wall clock, and the package is not accepted.

**Five of the six unclosed findings are one shape: I fixed the case shown, not the invariant.**
Shallow clones — refused at `New`, never re-checked, and `git replace --graft` reaches the identical
whole-tree payload without being shallow at all. Quoted paths — `unquotePath` added, while
`TrimSpace` still records a path that does not exist. The greedy `VD-` regex — relabelled a "stated
limitation", stated in the direction where it LOSES an id, when the real behaviour FABRICATES one
(`VD-<slug>-<6>` abutting any six-letter word: `-driven`, `-review`, `-change`).

LESSON[fix-the-example-not-the-invariant]: this class did not shrink between rounds. Every one of my
five repairs made its named reproduction fail, and every one left a second route to the same harm
open. The reproduction is the WEAKEST possible statement of a defect, and it is the thing my
attention lands on. Compiled response owed: before closing any finding, write down the HARM in the
finding's own words, then enumerate routes to that harm — the reproduction is one route, never the
set.

**Three findings are specifically about how I repair:**

1. *My anti-vacuity guard produced vacuity.* I added a guard to the detached-HEAD test precisely so
   it could not pass for the wrong reason. `git branch --contains <sha> --all` always prints the
   `* (HEAD detached from …)` pseudo-entry, so the guard fires every time: the test SKIPS 100% of
   the time, structurally, on every machine. One skip in 50 tests, and it is the only proof of the
   newest commit's invariant. `invariant-lint` verifies a cited test EXISTS; nothing verifies it RUNS.

2. *I repeated round 1's exact error inside the fix for it.* Round 1's HIGH-1 was a comment claiming
   content could not contain 0x1e — false. My replacement asserts "git refuses NUL in a commit
   message" — also false: `fast-import` accepts it and `fsck` only warns. The framing survives
   because git's pretty-printer truncates `%B`/`%s` at the NUL, silently dropping the rest of the
   body and any citation after it. Two of the three reviewers over-generalised the same way (they
   tested `commit`, `commit-tree`, `hash-object` and stopped); the adjudicator caught all three of us.
   LESSON[cannot-claims-need-an-adversary-not-a-check]: I verified NUL-refusal three ways and still
   got it wrong, because I enumerated the paths I already knew. "Cannot" is a claim about ALL paths,
   and the ones that falsify it are by definition the ones not thought of.

3. *I broke an invariant while fixing another.* Widening `Commits` to `--exclude … --all` left `Tips`
   at `refs/heads refs/tags refs/remotes`, so ingested detached-HEAD and `refs/pull/*` commits now
   appear in no cursor — reviving round 1's finding 15 through a different door. Plus the parent
   SPEC still prescribes `--branches --tags --remotes`, contradicting the child SPEC in the same
   repo, because I updated one and not the other.

**What this says about the project, which is the point of vera being its own testbed.**

Iterating fixes does NOT converge here. Round 1 → 15 findings. Round 2 → 21. The fix rate and the
introduction rate are roughly equal, and both rounds were on code that was `make check` GREEN with an
author-run mutation sweep. This is not a "try harder" problem: I have now been careful twice, and
being careful produced defects at the same rate as being fast.

What HAS converged, every time, is mechanism. The empirical record in this repo is unambiguous:
lesson classes answered with a blocking script + self-test recurred ZERO times; classes answered with
prose recurred 3-5 times. Round 2's own findings say which mechanisms are now earned:

- **`make mutants`** (the last unbuilt anti-recurrence gate) would have caught MED-7 (`.UTC()`
  unpinned), MED-6 (gitcmd's lock unenforced), MED-8 (missing banned args), and all five surviving
  dead branches — roughly eight of round 2's findings, mechanically, on every run, forever.
- **A skip detector.** A test that skips is not coverage. HIGH-1 is exactly this and `invariant-lint`
  cannot see it. Perhaps twenty lines.
- **A cross-SPEC contradiction check.** HIGH-4 is two SPECs in one repo prescribing opposite things.

LESSON[careful-does-not-scale-mechanism-does]: after two adversarial rounds the honest conclusion is
that my defect-introduction rate is a constant I cannot lower by intention. The only lever that has
ever moved it in this repo is converting a class into something that fails the build. Round 3 by hand
would be the third instance of the thing that has not worked twice.
