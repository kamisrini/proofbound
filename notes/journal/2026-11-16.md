## Plan validation (author-side pre-review, not the Law 9 verdict)

The owner asked for a validation pass after switching models. Checked against the codebase, not the
prose. Findings and fixes:

1. **Architecture (major).** The plan proposed a "normalized IR" + a new top-level connector. The
   P5 intent connector is already a *provider framework* (`records`, `specdir` → canonical BD/BR/CI
   `Revision`s; `Sync` validates + topologically orders; `Resolve(tree, id)` binds `Intent:`
   trailers), and its SPEC anticipates "a later API provider". `specdir` is the exact prior art
   (committed markdown at a tree → regex grammar → canonical revisions). Corrected: the SDD
   connector is a **third intent provider** (`intent.sdd`) driven by JSON profiles, mapping onto
   the existing canonical model; `ErrUnmappable` is the answer to a kit that cannot map, not a
   reason to widen the model. VD, RELEASE-PLAN table, and plan rewritten accordingly.
2. **Digest normalization conflicted with the P5 contract** (`artifact_sha256` = exact committed
   bytes for committed-file providers). Dropped; churn is handled by profile scope + granularity.
3. **Intent home for the R2 build was missing** — every CI must target a BR obligation; M0 now
   authors `BD`/`BR-sdd-warranty-*`.
4. **Law 8**: profiles pinned to JSON (no YAML dependency without a VD).
5. **Spec invariant** "production providers are exactly `records` and `specdir`" must be amended
   in M0 (non-author review), not discovered in M1.
6. **Route matrix**: `sync intent sdd` touches `kernel/internal/cli` (a routed dir) — regenerate
   after committing. Compiled into the plan's "Known gotchas".
7. **ROADMAP self-contradiction** ("recommended next step is #2b" vs R2 = SDD) — fixed.
8. **CI prose said "supersedes" while the JSON `supersedes` was empty** — fixed to "follows";
   self-digest recomputed.

LESSON: class=validation-reads-head response=notes/state.md + plan "Known gotchas"
`proofbound sync intent records` reads the committed **`HEAD` tree** (`git ls-tree … HEAD`), so an
uncommitted record is invisible to it. I ran `sync` after authoring the new CI, saw
`appended=3 … exit 0`, and reported the record "validated" — the 3 were older committed records the
dev ledger had not seen; my CI was never read. A later `appended=0` on changed bytes looked like
dedupe-on-identity; it was the same cause. Real validation: a throwaway `go test -overlay` test
feeding the working tree through the real `records` provider + `intent.Sync` batch validation
(36/36 pass; the CI ingests as `change_intent.recorded`). Nothing in the repo was touched. First
sighting → journal + state.md. If seen again, compile it: a `scripts/` worktree intent-validation
check (or a `sync --worktree` flag) so a green `sync` can never be mistaken for validation of an
unstaged file.

LESSON: class=plan-drift-seed response=plan + VD rewrite
A plan written from the product conversation, before reading the package SPEC it extends, invented
a parallel model ("normalized IR") for a thing the kernel already has (the canonical intent model +
provider interface). Law 2 in plan form. The fix was mechanical once the SPEC was read; the
process fix is already a law (Law 6: spec before code) — the amendment is *read the adjacent SPEC

Also settled while validating: `IdempotencyKey = (source, native_id, content_sha)` and
`IsRevisionOf` = same subject, different content — so an in-place spec edit **is** a new revision
event once committed, which is what M4's drift projection rests on.
