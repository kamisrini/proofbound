## Two calibration controls were not enough, and the reason generalises

`make mutants` shipped with a neutral control (a comment — must survive) and a compile control (an
undefined symbol — must be invalid). Both are real. Both were insufficient, and I nearly stopped
there.

If `go test` were silently not running — a wrong package pattern, a swallowed exit code — the
neutral control still survives (correct) and the compile control still comes back invalid (correct),
because BOTH are decided by the compiler. The harness would have declared itself calibrated having
never run a single test, and every "no survivors" would have been a false negative. So there is now
a third: an injected always-failing test that must come back KILLED. It can only pass if a real test
really failed.

LESSON[controls-not-independent]: plural controls are not independent controls. Two checks that
resolve through the same mechanism cannot distinguish that mechanism working from that mechanism
being absent — they fail and pass together. A control set has to span the DIMENSIONS a harness can
be broken in, not just have more than one member. Ask of any control pair: is there a single failure
that both would report as healthy?
Compiled response: `tools/mutants/runner.go` `calibrate()` runs three controls across two
dimensions (compile-time and test-time), and `scripts/mutants.sh` refuses to report a score if the
calibration line is absent from the output. The general form is owed and recorded: `figure-provenance`
and `skip-lint` each check ACCOMPANIMENT rather than TRUTH, and no control anywhere in this repo
currently spans that second dimension.

## The reviewer's proposed remedy was wrong, and I nearly applied it verbatim

Round 2's fix list for the citation-fabrication defect said: "reject any match whose full run
contains more than one 6-char-tail candidate." That is a precise, plausible, well-argued remedy from
a reviewer who had just found fifteen real defects — and it is wrong. It would have refused
`VD-commit-is-durability-6p29qf`, a real decision id, because "commit" is six characters.

I found that only by checking the proposed rule against every real suffix shape in `docs/decisions`
before implementing it. The correct fix is a non-greedy suffix quantifier, which additionally
RECOVERS the real id in the abutting case rather than dropping it — strictly better than both the
defect and the proposed remedy.

LESSON[reviewer-remedy-unverified]: a verified FINDING does not make its proposed FIX verified. The
finding was proven with a reproduction; the remedy was reasoning, and reasoning is what this project
keeps getting wrong. Adversarial review earns trust about what is broken, never about what to do
about it — and the credibility of fifteen correct findings is exactly what makes the sixteenth
suggestion dangerous.
Compiled response: none scriptable — this is a review question, recorded alongside the existing one:
for every finding, verify the REMEDY against real data before applying it, not only the defect.

## gitcmd passes the mutation gate — and what the triage was actually worth

`make mutants PKG=./internal/connector/git/gitcmd/...` is GREEN: 135 candidates, 106 killed, 16
survivors, every one declared with a reason. First package in the repo through that gate.

The triage was worth more than the number. Three things came out of it that no amount of reading
would have produced:

**A guard I would have deleted turned out to be load-bearing.** Five survivors sat on
`unquotePath`'s shape check, and by reasoning it looks like an optimisation: the fallback
(`strconv.Unquote` fails → return the path verbatim) appears to give the same answer as the early
return. It does not, because `Unquote` also accepts BACKQUOTED strings — so without the guard, a git
path literally named `` `abc` `` is silently unquoted to `abc`. A recorded path that does not exist,
which is HIGH-2's harm arriving by a third route.

**Two guards I would have defended turned out to be dead**, and the sweep proved it rather than
suggesting it: `parseLog`'s empty-input early return (the split, leading-separator check and modulo
already handle `""`), and `parseRecord`'s `TrimLeft(f[0], "\n")` (the inter-record newline lands at
the end of the previous chunk, never the start of a sha). Both carried comments explaining their
purpose, which is what made them read as load-bearing.

LESSON[reasoning-cannot-rank-guards]: I could not tell, by reading, which of three defensive guards
were dead and which was protecting against a real harm — and I got the ranking exactly inverted. The
mutation result is not a coverage metric here; it is the only thing that distinguished them.
Compiled response: `make mutants` exists and gitcmd is gated. The general form is recorded as owed:
`git`, `core` and `store` have never been swept, so the same inversion may be sitting in all three.

**And an assertion of mine passed for the wrong reason, environment-dependently.** `New("")` asserted
only `err != nil`. With the guard removed, an empty dir means "inherit the CWD" — so the verdict
depends on whether the test runs inside a git work tree. It does in the repo (mutant would die) and
does not in the harness's scratch copy (mutant survives). The sweep found it precisely BECAUSE it
runs somewhere else.
LESSON[environment-dependent-verdict]: a test whose pass/fail depends on where it runs is not a test,
and the dependency can be invisible — here it entered through a DEFAULT (empty dir → CWD) rather than
through anything the test mentions. Running the suite from a different directory is a cheap way to
find this class, and the mutation harness does it for free.

## Round 2's MED set closed — and I broke the numbering rule I had been enforcing all day

Nine of nine, across two commits. Eleven mutations, eleven killed by the right test. Two items are
worth more than their entries.

**MED-5 was worse than the reviewer described, and reproducing first is why I know.** Round 2 said
`git replace --graft` reaches the shallow harm without being shallow. It does — and it causes THREE
harms simultaneously: the replacement commit reports the whole tree, the ORIGINAL commit is rewritten
to report the whole tree too, and its two ancestors DISAPPEAR from the listing entirely. Two flags
are needed (`--no-replace-objects` and `--exclude=refs/replace/*`) and I verified neither alone
restores true history. Had I fixed from the description rather than the reproduction, I would have
shipped one flag and believed it.

**MED-3's premise was the load-bearing claim of the entire framing argument, and it was false.**
G-INV-1 said "git refuses NUL in a commit message". `commit`, `commit-tree` and `hash-object` do —
`fast-import` does not, and `fsck` only warns. The framing survives because git's pretty-printer
TRUNCATES `%B`/`%s` at the NUL. That is now stated and pinned, and the price is recorded: everything
after the NUL is silently dropped, so a decision id there is never seen. Second time this session a
"git refuses X" claim of mine turned out false (the first was `0x1e`), which is the same lesson
arriving by the same route.

**Then I did the thing I have been policing.** Adding the object-replacement invariant, I INSERTED it
as G-INV-12 and pushed "path bytes" and "a citation is never fabricated" to 13 and 14 — silently
invalidating every reference to those two numbers. This is the identical defect the Build Laws hit on
2026-08-11. I had enforced append-only numbering all day, written the note about it in this very
SPEC, and quoted the laws' version of it in a commit message hours earlier.

LESSON[knowing-a-rule-does-not-prevent-breaking-it]: I violated an append-only rule I had authored,
enforced, and explained, within the same editing session — while adding an invariant whose whole
subject is silent data corruption. The rule was not forgotten; it simply did not fire at the moment
of the edit, because nothing made it fire. This is the strongest single piece of evidence in the

Compiled response OWED, and named: the Build Law namespace has `law-citation-lint`; the invariant

guard it.
